## Задание 1. Программа создания и управления хеш-таблицей

### 1.1. Условие задачи

Разработать программу создания и управления хеш-таблицей для быстрого поиска данных по ключу (асимптотика в лучшем случае O(1)). Исходные данные — массив из 20 записей. Реализовать операции: создание таблицы, вставка, удаление, поиск, вывод, рехеширование. Управление — посредством текстового меню.

### 1.2. Задание варианта

**Вариант 4.** Метод разрешения коллизий — цепное хеширование. Структура записи двоичного файла: **Владелец автомобиля**: номер машины (ключ), марка, сведения о владельце, сведения об угоне (логического типа).

### 1.3. Хеш-функция

Мультипликативная функция Кнута (целочисленная форма):

```
h(k) = k · 2654435761 mod 2^64
индекс = h(k) % m, где m — простое число
```

**Свойство:** `2654435761 mod 11 = 9 ≠ 0`, поэтому `h(k) % 11 == 0` равносильно `k % 11 == 0`. При `capacity = 11` ключи, кратные 11, попадают в бакет 0.

**Реализация** (`src/record_car.cppm`):

```cpp
static std::size_t hash_key(std::uint64_t k) noexcept {
    return static_cast<std::size_t>(k * 2654435761ull);
}
```

Переполнение `uint64_t` определено (модулярная арифметика). Константа `2654435761` — 32-битная версия константы Кнута (золотое сечение).

### 1.4. Структура записи

#### Коэффициент нагрузки при рехешировании

Порог: `LOAD_FACTOR_MAX = 0.75`. Рехеширование срабатывает при `size / capacity > 0.75`:

- при `capacity = 11`: после 9-й вставки (`9/11 = 0.818 > 0.75`) → `rehash(23)`;
- при `capacity = 23`: после 18-й вставки (`18/23 = 0.783 > 0.75`) → `rehash(47)`.

Новый размер — `next_prime(2 × capacity)`: `next_prime(22) = 23`, `next_prime(46) = 47`.

## Задание 2. Программа использования хеш-таблицы для доступа к записям двоичного файла

### 2.1. Условие задачи

Разработать программу, использующую хеш-таблицу для организации прямого доступа к записям двоичного файла. Программа управляет двумя структурами: файл и хеш-таблица. Реализовать операции: чтение записи из файла и вставка в таблицу, удаление записи из таблицы и из файла, поиск записи в файле по ключу. Подготовить функцию генерации двоичного файла размером 100, 1000, 10000 записей. Замерить число сравнений при поиске заданного ключа в первой, последней и средней записи.

### 2.2. Задание варианта

**Вариант 4.** Цепное хеширование. Структура записи — владелец автомобиля (номер машины, марка, сведения о владельце, сведения об угоне).

### 2.3. Архитектура

Три заголовочных модуля:

1. **`file_io.cppm`** — управление двоичным файлом:
   - `create_empty()`, `count()`, `read(idx)`, `write(idx, r)`, `append(r)`;
   - `mark_deleted(idx)` — tombstone-удаление (флаг `deleted = true`);
   - `compact()` — физическая компактификация.

2. **`hash_table.cppm`** — хеш-таблица (из задания 1).

3. **`file_hash.cppm`** — связка «файл + таблица»:
   - `FileHashIndex(BinaryFile<Rec>&)` — конструктор, `rebuild()`;
   - `find(key)` → `record_no` → `read(record_no)`;
   - `insert(r)` — `append` + `table_.insert`;
   - `remove(key)` — `mark_deleted` + `table_.erase` (tombstone, `record_no` не меняются);
   - `compact()` — `file_.compact()` + `rebuild()`.

Утилиты:

| Файл              | Назначение                                             |
| ----------------- | ------------------------------------------------------ |
| `src/bin_io.cppm` | `write_record` / `read_record` (бинарная сериализация) |
| `src/gen.cpp`     | генератор `gen [N] [filename]`                         |
| `src/dump.cpp`    | читаемый вывод `dump [--table]`                        |

### 2.4. Tombstone-удаление

При удалении запись **не сдвигается**, а помечается `deleted = true`. Это сохраняет `record_no` остальных записей, поэтому `rebuild` после каждого удаления не нужен.

**Компактификация** (`compact`) физически удаляет tombstone-записи, но меняет `record_no` → требует `rebuild()`.

### 2.5. Генератор файлов

```bash
./build/clang-debug/gen 100    data/n100.bin
./build/clang-debug/gen 1000   data/n1000.bin
./build/clang-debug/gen 10000  data/n10000.bin
```

Детерминированный seed (`42`) — повторный запуск даёт байт-в-байт тот же файл (для воспроизводимости табл. 11).

Размеры файлов: `11200`, `112000`, `1120000` байт (`100`, `1000`, `10000` × `sizeof(CarOwner) = 112`).

### 2.7. Выводы

**Подтверждение сложности O(1):** число сравнений при поиске — **1** для N = 100, 1000, 10000, независимо от позиции записи в файле. Это экспериментально подтверждает асимптотику O(1).

Теоретически при коэффициенте нагрузки `α = n/m ≤ 0.75` ожидаемое число сравнений при успешном поиске в цепочках — `1 + α/2 ≈ 1.375`. Для конкретных ключей (first/middle/last) в файлах с фиксированным seed (`42`) длина цепочки оказалась 1.

**Без хеш-таблицы** (линейный поиск в файле) потребовалось бы до N сравнений: для N = 10000 — до 10000 сравнений вместо 1.

**Выводы по полученным знаниям:** разработана хеш-таблица с цепочками, выбрана хеш-функция (Knuth multiplicative), реализовано управление коэффициентом нагрузки через `rehash`. Хеш-таблица интегрирована с бинарным файлом; tombstone-удаление сохраняет `record_no`, `compact` физически сжимает файл с перестройкой индекса. Экспериментально подтверждена асимптотика O(1).
